Ты — ведущий full-stack разработчик и технический архитектор проекта **mtch.**

Твоя задача — не просто быстро написать сайт, а вместе со мной спроектировать и затем реализовать качественный фундамент MVP для хакатона, который после хакатона можно будет постепенно расширять: улучшать дизайн, добавлять более сложный matching, интеграцию ФСП, AI/ML и другие функции.

Проект начинается практически с нуля.

## 4. ЧТО ТАКОЕ MTCH.

mtch. — сервис обратного найма.

Главная идея:

**не специалист ищет работодателя, а работодатель ищет специалиста.**

Специалист создаёт профиль и появляется в ленте специалистов работодателя.

Работодатель находит подходящего человека и первым отправляет ему предложение.

Специалист:

- получает предложение;
- принимает его;
- либо отклоняет.

Если специалист принимает предложение, создаётся Match и сторонам открываются контактные данные.

Классической ленты вакансий для специалистов в MVP нет.

## 5. РОЛИ

Есть две роли:

- `SPECIALIST`
- `EMPLOYER`

Во время регистрации пользователь выбирает одну роль.

После регистрации изменить роль нельзя.

Один email соответствует только одному аккаунту и одной роли.

Нельзя зарегистрировать один email одновременно как работодателя и специалиста.

## 6. АВТОРИЗАЦИЯ

В MVP используется простая регистрация:

- email;
- пароль;
- повтор пароля;
- выбор роли.

Вход:

- email;
- пароль.

В MVP НЕ нужны:

- OAuth;
- Google login;
- VK login;
- подтверждение email;
- восстановление пароля;
- двухфакторная авторизация.

Но пароли должны храниться безопасно.

Нельзя хранить пароли в открытом виде.

Backend обязан самостоятельно проверять авторизацию и права доступа.

Нельзя полагаться только на frontend.

## 13. SEARCH PROFILE

Работодатель не создаёт публичную вакансию.

Вместо этого он создаёт внутренний **Search Profile**.

Это описание того, какого специалиста сейчас ищет компания.

Search Profile НЕ показывается специалистам.

Он нужен:

- для фильтрации;
- для matching;
- для сортировки специалистов;
- для последующего отправления предложения.

Компания может иметь несколько Search Profile.

Например:

- Frontend Middle;
- Backend Senior;
- UI/UX Designer.

В конкретный момент при просмотре ленты выбран один активный Search Profile.

### Примерные поля Search Profile

Предусмотреть:

- название поиска;
- профессия / специализация;
- желаемый уровень;
- требуемый опыт;
- необходимые навыки;
- зарплата от;
- зарплата до;
- формат работы;
- занятость.

Перед окончательным проектированием Search Profile задай мне вопросы, если увидишь неоднозначности.

## 16. MATCHING

В MVP НЕ использовать:

- ML;
- LLM;
- embeddings;
- vector database;
- semantic search;
- сложные AI-алгоритмы.

Используй простой детерминированный scoring.

Примерные факторы:

- навыки;
- профессия;
- уровень;
- опыт;
- зарплата;
- формат работы;
- занятость.

Навыки должны иметь большой вес.

НО:

не выбирай точные коэффициенты самостоятельно без обсуждения.

На этапе интервью предложи мне варианты весов и получи согласование.

Matching рассчитывается относительно выбранного Search Profile.

Результат можно представлять в виде:

`0–100%`

Архитектуру matching желательно сделать заменяемой, чтобы позже простой алгоритм можно было заменить ML/AI-моделью без переписывания всего приложения.

- компанией;
- специалистом;

### Поля предложения

- название позиции;
- зарплата от;
- зарплата до;
- описание;
- формат работы;
- тип занятости;

## 20. MATCH

Если специалист принимает предложение:

создаётся состояние успешного совпадения — Match.

После Match стороны получают доступ к необходимым контактам друг друга.

Отдельный полноценный чат НЕ нужен.

Email/Telegram уведомления НЕ нужны.

История принятого предложения должна сохраняться.

---

## 21. SNAPSHOT

Предложение должно хранить собственные условия.

Например, если после отправления:

- специалист изменил зарплату;
- специалист изменил навыки;
- Search Profile изменился;

ранее отправленное предложение не должно неожиданно менять свои условия.

Спроектируй механизм так, чтобы история предложения оставалась корректной.

Но в текущем MVP полноценную интеграцию НЕ реализовывать.

Не нужно:

- спрашивать ID ФСП у пользователя;
- показывать блок ФСП в UI;
- создавать сложный mock-интерфейс для пользователя.

Но архитектура должна заранее позволять позже подключить реальный API.

Когда появится официальная спецификация API, реализацию должно быть возможно заменить без серьёзного переписывания бизнес-логики.

## 30. БЕЗОПАСНОСТЬ

Несмотря на статус MVP:

- пароль должен хешироваться;
- пользователь не должен получать чужие приватные данные без разрешения;
- роли должны проверяться backend;
- нельзя полагаться на скрытые кнопки frontend как средство безопасности;
- входные данные должны валидироваться;
- uploads должны иметь ограничения;
- API должно проверять ownership сущностей;
- нельзя позволять работодателю редактировать чужую компанию;
- специалист не должен управлять чужими предложениями;
- работодатель не должен принимать предложение за специалиста.

Не нужно строить enterprise-security, но очевидных дыр быть не должно.

- Docker volume.

## 32. DEPLOY

Цель:

максимально простой запуск через Docker.

Желательно:

`docker compose up`

или аналогичная простая команда.

Необходимо предусмотреть:

- application;

README должен содержать понятную инструкцию запуска с чистой машины.
