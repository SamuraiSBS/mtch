# mtch. — план MVP

Статус: **базовый MVP реализован и проверен локально 1 октября 2026 года**. Дата планирования: 30 сентября 2026 года. Публичное размещение и ФСП остаются отдельными следующими этапами.

## Цель и сроки

- К **2 октября 2026**: реализовать весь функциональный объём MVP из `mtch_codex_master_prompt.md`, запустить его локально через Docker и подтвердить основные сценарии тестами и ручной проверкой.
- К **11 октября 2026**: сделать сервис публично доступным для демонстрации. Домен и сервер владелец предоставит позже.
- **5 октября 2026** ожидаются спецификация/мок API ФСП и материалы Федерации. Подтверждённые достижения ФСП должны участвовать в демонстрации 11 октября; это отдельная работа после базового MVP, зависящая от полученной спецификации.

## Зафиксированные решения

- Две неизменяемые роли: `SPECIALIST`, `EMPLOYER`; один email — один аккаунт.
- Профиль специалиста публикуется при сохранении. Для сохранения обязательны имя, фамилия, специализация из справочника, минимум один навык из справочника, загруженный аватар и обе границы месячной зарплаты в ₽. Начальный статус — `OPEN_TO_OFFERS` («открыт к предложениям»). Статус `NOT_LOOKING` исключает профиль из ленты, но не удаляет историю и не запрещает принять уже полученное предложение.
- Специализации, города и навыки выбираются из справочников. Формат работы, занятость и тип сотрудничества — по одному значению на поле.
- Профили видят только зарегистрированные пользователи. Лента и действия поиска доступны работодателю. До Match контакты специалиста и компании скрыты; остальные данные профиля доступны зарегистрированным пользователям. Соцсети компании считаются контактными каналами. После Match работодатель видит email аккаунта и Telegram специалиста, специалист — email аккаунта работодателя, заполненные контакты и соцсети компании. Отдельный телефон специалиста не нужен.
- Один работодатель владеет одной компанией. Для её первого сохранения обязательны название, краткое описание, формат работы, год основания, размер, сфера деятельности и логотип. Сайт, контактные email/Telegram/телефон, дополнительные фотографии и ссылки соцсетей необязательны; email аккаунта работодателя всегда доступен после Match.
- Search Profile может существовать без «активации»; работодатель выбирает его для текущего просмотра ленты. Все специалисты, кроме `NOT_LOOKING`, остаются в выдаче, включая 0% совпадения. Выбранные фильтры объединяются через AND, выдача сортируется по проценту и разбивается на страницы.
- Веса scoring: навыки 40, профессия 20, уровень 10, опыт 8, зарплата 8, формат работы 7, занятость 7. Навыки Search Profile равнозначны. Правила расчёта описаны в `ARCHITECTURE.md`.
- Предложение создаётся из Search Profile с автозаполнением и возможностью исправить поля до отправки. После отправки его условия неизменяемы; доступны только разрешённые переходы статуса. Все поля предложения обязательны.
- Одновременно одному специалисту от одного работодателя может быть отправлено только одно предложение. После `REJECTED` или `WITHDRAWN` можно отправить новое. После `ACCEPTED` повторное предложение этой паре запрещено. Специалист может иметь несколько Match с разными работодателями.

## Рабочие допущения для утверждения вместе с планом

Эти решения нужны для детерминированной схемы и API. При утверждении плана владелец подтверждает их либо указывает поправки:

1. Остальные поля специалиста, кроме перечисленных выше обязательных, необязательны. Дата рождения нужна для показа возраста, но её отсутствие не блокирует публикацию; в карточке тогда нет возраста.
2. В Search Profile обязательны название, специализация, уровень, минимум опыта, минимум один навык, обе границы зарплаты, формат работы и занятость. Незаполненный Search Profile не создаётся.
3. Если у специалиста не заполнено необязательное поле, соответствующий фактор scoring даёт 0 баллов. Нормализация суммы весов не выполняется.
4. Поля компании и специалиста можно позже редактировать; ранее отправленные предложения и их snapshots остаются неизменными.
5. Работодатель может отозвать только `SENT`; специалист может принять или отклонить только `SENT`. Состояния `ACCEPTED`, `REJECTED`, `WITHDRAWN` конечные.
6. Поле PDF-резюме присутствует в модели и интерфейсе как недоступная к загрузке возможность; фактическая загрузка PDF не входит в базовый MVP.
7. Работодатель не может отправить новое предложение специалисту со статусом `NOT_LOOKING`, даже зная прямой URL профиля. Старое предложение специалист вправе принять.
8. Несколько явно выбранных навыков фильтра ленты означают наличие всех этих навыков у специалиста. Социальные ссылки компании скрываются до Match как контактные каналы.
9. Размер компании выбирается из диапазонов `1–10`, `11–50`, `51–200`, `201–1000`, `1000+` сотрудников.

## Критерий готовности MVP

Через `docker compose up --build` из чистой машины поднимаются приложение и PostgreSQL с постоянными volume для БД и медиа; миграции проходят; идемпотентный seed создаёт примерно 20 разнообразных специалистов, 4 компании, несколько Search Profile и demo-аккаунты. Пользователь может пройти регистрацию, войти, создать/изменить профиль или компанию, выбрать Search Profile, отфильтровать и просмотреть ленту, отправить предложение, принять/отклонить/отозвать его и увидеть контакты только после Match. Тесты, typecheck, lint, build и критические smoke-проверки проходят. API и запуск документированы.

## Зависимости и риски

- Срок до 2 октября очень плотный для полного объёма. Приоритет исполнения — сквозные работающие сценарии и проверки каждого этапа; функции из согласованного объёма не удаляются молча.
- Публичный деплой зависит от доступа к серверу и домену. Пока их нет, проверяется воспроизводимый Docker-запуск.
- Демонстрация достижений ФСП зависит от спецификации 5 октября. До неё нельзя фиксировать формат данных и механизм идентификации участника как подтверждённый.
