# API mtch. MVP

Статус: **проект контракта на утверждение**, 30 сентября 2026. Базовый префикс: `/api/v1`. Все ответы — JSON, кроме выдачи медиа. API реализуется Route Handlers, а серверные правила и доступ проверяются в сервисном слое. Конкретные внутренние маршруты Better Auth скрыты за приложенческим auth-контрактом либо защищены теми же правилами регистрации роли.

## Общие правила

- Сессия передаётся в защищённой HttpOnly cookie. Все маршруты ниже, кроме регистрации, входа и health, требуют входа.
- Роль берётся из серверной сессии, а не из заголовка/тела запроса. ID компании и профиля поиска дополнительно проверяются по ownership.
- `POST` создания возвращает `201`, `GET` — `200`, изменение — `200`, удаление/действие без тела — `204`. Ошибки: `400` синтаксис, `401` нет сессии, `403` неверная роль, `404` недоступный/несуществующий объект, `409` конфликт состояния/дубликат, `413` большой файл, `415` тип файла, `422` валидация.
- Ошибка имеет форму `{ "error": { "code": "OFFER_ALREADY_SENT", "message": "...", "details": {} } }`. Детали не содержат секретов и внутренних путей.
- Списки используют `page` (с 1) и `pageSize` (по умолчанию 20, максимум 100); ответ `{ "items": [...], "page": 1, "pageSize": 20, "total": 42 }`.
- Денежные поля: целые ₽ за месяц. Для каждого диапазона обе границы обязательны, положительны, `min <= max`. Клиенту не предлагается выбор налогового режима.
- Входные `professionId`, `cityId`, `skillIds` ссылаются на справочники; неизвестные/неактивные значения не принимаются для новых записей. Обновление идёт в одной транзакции с таблицами навыков и медиа.
- Никакой обычный DTO не включает контакты до Match. Telegram специалиста, контактные поля и социальные ссылки компании выдаются только через endpoint контактов Match. Ссылки на портфолио, GitHub и Behance/GitLab контактами не считаются и видны зарегистрированным пользователям.

## Authentication

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `POST /auth/register` | гость | `{ email, password, passwordConfirmation, role }`; одна роль навсегда, email уникален; создаёт сессию и возвращает `{ user: { id, email, role } }` |
| `POST /auth/login` | гость | `{ email, password }`; создаёт сессию |
| `POST /auth/logout` | вошедший | удаляет текущую сессию |
| `GET /auth/me` | вошедший | ID, email, роль, наличие профиля/компании |

OAuth, подтверждение email и восстановление пароля не включены. Backend принудительно нормализует email, валидирует роль при любом пути регистрации и не предоставляет endpoint изменения роли.

## Справочники и health

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `GET /catalogs/professions` | вошедший | активные специализации `{ id, name }` |
| `GET /catalogs/cities` | вошедший | активные города |
| `GET /catalogs/skills` | вошедший | активные навыки |
| `GET /health` | публичный | готовность приложения и БД, без секретных данных |

Справочники только читаются из UI; они наполняются seed и расширяются данными БД/миграциями.

## Специалист

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `GET /specialists/me` | `SPECIALIST` | свой профиль или `404`, если ещё не создан |
| `POST /specialists/me` | `SPECIALIST` | первое сохранение и автоматическая публикация |
| `PUT /specialists/me` | `SPECIALIST` | полное обновление своего профиля |
| `GET /specialists/{userId}` | любой вошедший | видимый профиль без контактов; для самого владельца собственные контакты доступны в `/me` |

Payload создания/обновления: `firstName`, `lastName`, `birthDate?`, `cityId?`, `avatarFileId`, `professionId`, `experience?`, `skillIds` (минимум 1), `level?`, `cooperationType?`, `about?` (до 500), `portfolioUrl?`, `githubUrl?`, `behanceGitlabUrl?`, `telegram?`, `salaryMinRub`, `salaryMaxRub`, `workFormat?`, `employmentType?`, `searchStatus`. Если `searchStatus` пропущен при создании, ставится `OPEN_TO_OFFERS`. `resume` показывается как поле с состоянием «загрузка позже»; endpoint загрузки PDF в базовом MVP отсутствует. Ответ публичного профиля вычисляет `age` при наличии `birthDate`, не отдаёт саму дату рождения без необходимости и никогда не отдаёт email/Telegram до Match.

## Компания работодателя

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `GET /companies/me` | `EMPLOYER` | своя компания с контактами и соцсетями |
| `POST /companies/me` | `EMPLOYER` | создать единственную компанию |
| `PUT /companies/me` | `EMPLOYER` | обновить свою компанию |
| `GET /companies/{id}` | любой вошедший | видимая информация компании без контактов |
| `POST /companies/me/photos` | `EMPLOYER` | привязать ранее загруженное фото своей компании |

Payload компании: обязательные `name`, `description` (до 500), `workFormat`, `foundedYear`, `sizeBand`, `industry`, `logoFileId`; необязательные `websiteUrl`, `contactEmail`, `telegram`, `phone`. Дополнительные фото и соцсети необязательны. Email аккаунта владельца не включён в публичный DTO компании.

## Search Profiles

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `GET /search-profiles` | `EMPLOYER` | список своих сохранённых профилей поиска |
| `POST /search-profiles` | `EMPLOYER` | создать профиль для своей компании |
| `GET /search-profiles/{id}` | владелец | подробности |
| `PUT /search-profiles/{id}` | владелец | обновить критерии |

Payload: обязательные `title`, `professionId`, `targetLevel`, `minimumExperience`, `skillIds` (минимум 1), `salaryMinRub`, `salaryMaxRub`, `workFormat`, `employmentType`. Компания уже должна существовать. `Search Profile` внутренний: специалист его не видит. Постоянного «активного» Search Profile нет — клиент передаёт ID при открытии ленты.

## Лента и matching

`GET /feed/specialists?searchProfileId=<uuid>&page=1&pageSize=20` — только `EMPLOYER`, и Search Profile обязан принадлежать его компании. Опциональные фильтры: `professionId`, `level`, `minimumExperience`, повторяемый `skillId`, `salaryMinRub`, `salaryMaxRub`, `workFormat`, `cityId`, `searchStatus`. Фильтры объединяются через AND; несколько `skillId` требуют все выбранные навыки. Фильтр зарплаты означает пересечение с заданным диапазоном; обе границы передаются вместе. Статус `NOT_LOOKING` всегда исключён. Фильтр статуса может выбирать только `ACTIVE` или `OPEN_TO_OFFERS`.

Сначала применяются ограничения доступности и фильтры, затем каждому оставшемуся специалисту рассчитывается score относительно переданного Search Profile. Сортировка: `score DESC, specialistId ASC`, потом пагинация. Кандидат с 0% остаётся в ленте, если соответствует явным фильтрам. Карточка отдаёт `userId`, avatar URL, имя, специализацию, уровень, опыт, основные навыки, зарплату и `matchPercent` 0–100; контакты отсутствуют. `GET /specialists/{userId}` показывает полную видимую часть профиля.

## Медиа

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `POST /media` | вошедший, по роли | multipart `file` + `kind` (`AVATAR`, `COMPANY_LOGO`, `COMPANY_PHOTO`); возвращает `{ fileId }` |
| `GET /media/{fileId}` | вошедший с правом на объект | выдаёт изображение с корректным MIME и безопасными заголовками |
| `GET /media/{fileId}?size=256\|64` | вошедший с правом на объект | уменьшенная версия аватара; для старых файлов возвращает имеющееся изображение |
| `GET /media/{fileId}/original` | владелец аватара | исходный файл без перекодирования |
| `DELETE /media/{fileId}` | владелец незакреплённого файла | удаляет временную загрузку |

Сервер проверяет размер, сигнатуру и MIME изображения, роль для `kind`, владельца при привязке и отсутствие обхода пути. Предел — 5 МБ на файл. Для аватара также требуются минимум 256 пикселей по каждой стороне и не более 24 мегапикселей. Загрузка аватара готовит оригинал и три WebP-версии, но публичная ссылка меняется только при сохранении профиля. Ошибки обработки имеют коды `INVALID_IMAGE`, `INVALID_IMAGE_SIZE`, `FACE_NOT_FOUND`, `BACKGROUND_REMOVAL_FAILED`, `IMAGE_PROCESSING_FAILED` или `IMAGE_PROCESSOR_BUSY` в обычной структуре `{ error: { code, message, details } }`. Логотип и аватар обязательны при сохранении соответствующей сущности. Файлы остаются в Docker volume. PDF upload в базовом MVP не включён.

## Предложения

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `GET /offers/outgoing` | `EMPLOYER` | свои отправленные предложения, пагинация и фильтр `status?` |
| `GET /offers/incoming` | `SPECIALIST` | свои входящие предложения, пагинация и фильтр `status?` |
| `GET /offers/{id}` | одна из сторон | собственные условия, статус, дата, snapshot контекста без скрытых контактов |
| `POST /offers` | `EMPLOYER` | создать и отправить предложение конкретному специалисту |
| `POST /offers/{id}/accept` | специалист-адресат | `SENT` → `ACCEPTED`, создать Match в той же транзакции |
| `POST /offers/{id}/reject` | специалист-адресат | `SENT` → `REJECTED` |
| `POST /offers/{id}/withdraw` | работодатель-владелец | `SENT` → `WITHDRAWN` |

`POST /offers` принимает `specialistUserId`, `searchProfileId`, `positionTitle`, `salaryMinRub`, `salaryMaxRub`, `description`, `workFormat`, `employmentType`, `message`. Все условия обязательны. UI предварительно подставляет поля из Search Profile; сервер сохраняет именно переданные проверенные значения и snapshot критериев поиска. Адресат должен иметь опубликованный профиль и статус `ACTIVE` либо `OPEN_TO_OFFERS` на момент отправки. Второе одновременное предложение той же пары и любое новое предложение после Match получают `409 OFFER_ALREADY_SENT`/`MATCH_ALREADY_EXISTS`. После `REJECTED`/`WITHDRAWN` новая отправка разрешена. `PUT/PATCH /offers/{id}` отсутствуют.

Переходы требуют актуального `SENT`, авторизации стороны и конкурентно безопасного обновления. Неверный переход возвращает `409 OFFER_INVALID_STATE`. Специалист может принять старое предложение при `NOT_LOOKING`. Другие его Match не мешают принятию.

## Match и контакты

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `GET /matches` | вошедший | список своих Match, пагинация |
| `GET /matches/{id}` | участник | связь с принятым предложением, дата |
| `GET /matches/{id}/contacts` | участник | контакты **второй стороны** |

Работодателю возвращаются email аккаунта специалиста и его Telegram, если заполнен. Специалисту возвращаются email аккаунта работодателя и необязательные контактные email/Telegram/телефон и социальные ссылки компании, если заполнены. Контакты не доступны по одному лишь ID принятого предложения и не входят в ленту, обычные профили или историю предложений. Отдельного чата и уведомлений нет.

## Документация и будущее ФСП

README даст пример запуска, demo-аккаунты и ссылку на этот контракт. Реальная схема endpoint для достижений ФСП появится после получения спецификации 5 октября и отдельного согласования. В базовом MVP нет публичного API для ФСП, mock-достижений или запроса ID ФСП у пользователя.
